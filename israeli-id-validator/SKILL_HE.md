זיהוי לפי קידומת הוא היוריסטיקה: מספר בן 9 ספרות שמתחיל ב-5 הוא על פי רוב ישות רשומה (המקור אומר ששתי הספרות הראשונות "על פי רוב" קשורות לסוג התאגיד, וכל הקודים הרשומים מתחילים ב-5), אך רק הרשם המנפיק הוא מקור סמכא. לעולם אל תדחו מספר, ואל תחליטו לאיזה שדה הוא שייך, בגלל הקידומת שלו: השתמשו בקידומת רק כדי לתייג מספר שהמשתמש כבר אמר שהוא מספר חברה. תעודת זהות אישית אינה ניתנת לזיהוי לפי קידומת.

### שלב 2: אימות דרך אלגוריתם ספרת ביקורת
אלגוריתם ספרת הביקורת של מספר זהות ישראלי (חל על כל הסוגים):

```python
import re


def validate_israeli_id(id_number: str) -> bool:
    """Validate Israeli ID number (TZ, company, amuta, etc.)"""
    # Discard ONLY the separators a human or a spreadsheet legitimately puts
    # inside an ID. Do NOT strip every non-digit: that silently turns
    # "62819482.1" into the VALID id 628194821, and turns "", "abc" and a row
    # of punctuation into "000000000". A validator that accepts garbage is
    # worse than one that rejects a real ID, because nobody finds out.
    # Do NOT gate on str.isdigit() either: it is True for Arabic-Indic digits
    # and superscripts, which either crash int() or validate as another value.
    # For the REASON (empty / malformed / bad check digit) use parse_id() in
    # scripts/validate_id.py; this compact version only answers yes or no.
    if not isinstance(id_number, str):
        return False        # an int has already lost its leading zeros
    # Trim whitespace, a CSV line break, the BOM and LRM/RLM/ALM at the ENDS only.
    # Inside the number a line break or bidi mark stays an error: bidi controls
    # can make the screen show different digits from the ones stored.
    EDGE = " \t\u00a0\r\n\u200b\ufeff\u200e\u200f\u061c"
    SEPARATORS = " -\u2010\u2011\u2013\u2014\u202f\u00a0\u00ad\u200b\u200c\u200d\u2060\ufeff"
    stripped = ''.join(c for c in id_number.strip(EDGE) if c not in SEPARATORS)

    if stripped == '' or not re.fullmatch(r'[0-9]{1,9}', stripped):
        return False        # malformed input, NOT an invalid ID

    id_str = stripped.zfill(9)

    if id_str == '000000000':   # passes Luhn but is never a real ID
        return False

    total = 0
    for i, digit in enumerate(id_str):
        # 1-based odd positions (indices 0,2,4,6,8) multiply by 1
        # 1-based even positions (indices 1,3,5,7) multiply by 2
        weight = 1 if i % 2 == 0 else 2
        val = int(digit) * weight
        if val > 9:
            val = val // 10 + val % 10     # Sum digits if > 9
        total += val

    return total % 10 == 0
```

### שלב 3: מתן תוצאה
למספרים תקינים: אומרים שהמספר עובר את ספרת הביקורת (מספר בנוי נכון, לא הוכחה שהונפק או ששייך לאדם), ומציינים את הסוג לפי הקידומת כתיוג סביר בלבד
למספרים לא תקינים: דיווח על אי-תקינות, הצגת הבדיקה שנכשלה, הצעת שגיאות נפוצות:
- ספרות מוחלפות
- ספרה חסרה/עודפת
- ספרת ביקורת שגויה

### שלב 4: יצירת מספרים לבדיקה (לשימוש בפיתוח)
לצורכי פיתוח ובדיקות, אפשר ליצור מספרי זיהוי תקינים:

```python
def generate_test_id(prefix: str = "") -> str:
    """Generate a valid Israeli ID number for testing."""
    import random, re
    if not re.fullmatch(r'[0-9]{0,8}', prefix):
        raise ValueError("prefix must be 0-8 ASCII digits")   # else an 11-digit "ID"
    if prefix == '00000000':
        raise ValueError("an all-zeros prefix can only yield 000000000")
    while True:
        base = prefix + ''.join(str(random.randint(0, 9)) for _ in range(8 - len(prefix)))
        if base != '00000000':      # would yield 000000000, which validation rejects
            break
    # Calculate check digit
    total = 0
    for i, digit in enumerate(base):
        weight = 1 if i % 2 == 0 else 2
        val = int(digit) * weight
        if val > 9:
            val = val // 10 + val % 10
        total += val
    check = (10 - (total % 10)) % 10
    return base + str(check)
```

הערה חשובה: מספרים שנוצרו מיועדים לבדיקות בלבד. לעולם אל תשתמשו במספרים אקראיים כזיהוי אמיתי. מספר שנוצר ועובר את ספרת הביקורת עשוי בכל זאת להיות תעודת זהות שהונפקה לאדם אמיתי, והמחולל לא יכול לדעת זאת, ולכן אל תחשפו מספרים כאלה לבני אדם או לצד שלישי (ראו מלכודות נפוצות).

## מלכודות נפוצות

- מספרי תעודת זהות ישראליים הם בדיוק 9 ספרות עם ספרת ביקורת מסוג Luhn (mod 10). סוכנים עלולים ליצור מספרים אקראיים בני 9 ספרות שנכשלים בבדיקת ספרת הביקורת.
- מספרי תעודת זהות עם פחות מ-9 ספרות חייבים להיות מרופדים באפסים משמאל. מספר כמו "12345678" הוא בעצם "012345678". סוכנים עלולים למחוק אפסים מובילים ולשבור ולידציה.
- מספרי תעודת זהות אינם מקודדים תאריך. אי אפשר להסיק מהמספר את תאריך הלידה, הגיל, שנת הלידה או מעמד התושבות. סוכנים שלמדו על מספרי SSN בארה"ב נוטים להמציא הנחה כזו.
- אין לסווג או לפסול תעודת זהות אישית לפי טווח הספרה הראשונה. אין במספר קידוד מעמד אזרחי מתועד (החלוקה הנפוצה ל"יליד הארץ מול תושב מול עובד זר לפי טווח" היא מיתוס). כל תעודת זהות אישית עוברת את אותה בדיקת Luhn ללא תלות בספרה הראשונה; יש להתייחס לכולן כמספרים רגילים בני 9 ספרות.
- שמירת PII ופרטיות בלוגים: לעולם אל תכתבו לוג של תעודת זהות בלי מסיכה בלוגי האפליקציה, בהודעות שגיאה, בטלמטריה או באירועי אנליטיקה. חוק הגנת הפרטיות תוקן באופן מקיף בתיקון 13 (בתוקף מ-14 באוגוסט 2025), ועל אירוע אבטחה חמור יש לדווח לרשות להגנת הפרטיות באופן מיידי (ראו הסעיף הבא). בהצגה של תעודה בהקשר לא מורשה (UI לדיבוג, כלים לתמיכה, קבלה ללקוח) הסתירו הכול חוץ מארבע הספרות האחרונות לכל היותר, למשל `xxxxx6782`. לפני שמירה במאגר לא הכרחי, השתמשו ב-HMAC-SHA256 עם pepper סודי שנשמר מחוץ למסד הנתונים, או ב-vault לטוקניזציה. hash רגיל בלי מפתח הוא לא הגנה: מרחב המספרים קטן מ-10^9 וספרת הביקורת מצמצמת אותו עוד, כך שאפשר להפוך את כל הטבלה בכוח גס תוך שניות.
- **ציות לחוק הגנת הפרטיות מעבר להיגיינת קוד הוא מחוץ לתחום של הסקיל הזה.** הרשות להגנת הפרטיות אוכפת את תיקון 13: ביולי 2026 היא הטילה את העיצום הכספי הראשון מאז כניסת התיקון לתוקף (256,000 ש"ח לאחר הפחתות בהתאם להוראות החוק, על קופת חולים) משום שלא דווח לרשות באופן מיידי על אירוע אבטחה חמור כנדרש בתקנות אבטחת המידע, והבהירה שהחובה קמה עם היוודע האירוע. מאגר של מספרי זהות צפוי להיות כפוף לתקנות האלה. לתוכנית הציות עצמה (רמות אבטחה, דיווח על אירועים, האם חייבים למנות ממונה על הגנת הפרטיות) השתמשו בסקיל `israeli-privacy-shield` והיוועצו בעורך דין; המאמת הזה מכסה רק את כללי הקוד שלמעלה.
- מספר העוסק של עצמאי אינו מספר ישות רשומה שמתחיל ב-5: מספר העוסק בתעודת עוסק פטור הוא לרוב תעודת הזהות האישית של בעל העסק בת 9 הספרות (מספרים שמתחילים ב-5 ניתנים עם רישום ברשות התאגידים). לכן שדה "מספר עוסק" שמקבל רק מספרים שמתחילים ב-5 פוסל עצמאים. קבלו את שתי הצורות בכל מקום שבו אתם מבקשים מספר עוסק; שתיהן עוברות את אותה ספרת ביקורת.
- המספר האישי הצבאי הוא מזהה נפרד שמונפק על ידי צה"ל והוא מחוץ לתחום של הסקיל הזה. אל תריצו אותו באלגוריתם ספרת הביקורת האזרחי: הסקיל לא מתעד עבורו ספרת ביקורת, ולכן תוצאת "תקין" או "לא תקין" חסרת משמעות.
- המספר 000000000 עובר את בדיקת Luhn (סכום הספרות הוא 0, מתחלק ב-10) אך לעולם אינו תעודה אמיתית. זו תקלת false positive נפוצה של ערך ברירת מחדל או שדה ריק: מחרוזת ריקה או עמודה עם ברירת מחדל מספרית מתרפדת באפסים ישירות אליו. דחו במפורש מספר של אפסים בלבד לפני שסומכים על תוצאת "תקין".
- **מספר בדיקה שנוצר יכול להיות תעודת זהות של אדם אמיתי.** מעבר בספרת הביקורת לא אומר דבר על כך שהמספר הונפק, והמחולל לא יכול לדעת זאת. אל תתנו למספרים שנוצרו להגיע לנתוני seed שיוצאים מהמחשב של המפתח, למיילים בסביבת בדיקות, לצילומי מסך, לתיעוד או לסביבות דמו. כשחייבים להציג מספר לבני אדם, השתמשו בדוגמה המפורסמת `123456782` או במספר שנכשל בכוונה בספרת הביקורת.
- **גם פלט ה-CLI שלכם הוא לוג.** מספר מלא שמודפס בטרמינל נשמר בהיסטוריית ה-shell ובלוגים של CI. השתמשו ב-`scripts/validate_id.py validate --mask`, שמדפיס רק את 4 הספרות האחרונות; `--verbose` מדפיס את כל הספרות ומסרב לרוץ יחד עם `--mask`.
- **הסרת כל תו שאינו ספרה לפני האימות היא הבאג שמייצר false positives.** זו שורת הקוד שנראית הכי טבעית, והיא גורמת ל-`62819482.1` לעבור אימות כ-`628194821`. מסירים רק קבוצת מפרידים מוגדרת, וכל דבר אחר נחשב קלט פגום ולא נמחק. זה ההבדל בין מאמת לבין מסנן.
- **מספר הפוך עדיין עובר את ספרת הביקורת.** המשקלים 1,2,1,2,1,2,1,2,1 זהים בשני הכיוונים, ולכן תעודה בת 9 ספרות שסדר הספרות בה התהפך (למשל מספר שנלקח מ-PDF בסדר חזותי, מ-OCR או ממערכת ישנה) תמיד עוברת: `287654321` הוא `123456782` הפוך, והוא עובר. רק ערך הפוך בן 8 ספרות (אחרי שהאפס המוביל נשמט) נכשל בדרך כלל. ספרת הביקורת לא יכולה לתפוס היפוך, ולכן השוו את המספר למה שהמשתמש רואה או הקליד, ולעולם אל תתייחסו ל"תקין" כהוכחה שסדר הספרות נכון. מאותה סיבה לעולם אל תסירו תווי override או isolate של כיווניות (U+202A עד U+202E, U+2066 עד U+2069): `"\u202e287654321"` מוצג על המסך כ-123456782 אבל נשמר כ-287654321.
- **תעודת זהות ישראלית היא לכל היותר 9 ספרות, ולכן דוחים קלט ארוך יותר במקום לתת לו להיכשל בבדיקת הביקורת.** `0000000018` אינו "תעודה לא תקינה", הוא בכלל לא תעודה, ואמירה למשתמש שהתעודה שלו שגויה שולחת אותו לחפש שגיאת הקלדה שאינה קיימת.

## פתרון בעיות

### שגיאה: "המספר נראה תקין אך לא מזוהה"
סיבה: ספרת הביקורת עוברת אך המספר לא הונפק בפועל
פתרון: האלגוריתם מאמת רק את הפורמט, לא את הקיום בפועל. רק הרשם המנפיק יכול לומר אם מספר הונפק: לחברות, שותפויות ועמותות, החיפוש של רשות התאגידים שבקישורי העזר. הסקיל לא מתעד חיפוש ציבורי לתעודות זהות אישיות.

### שגיאה: "תעודה נכשלת באימות אחרי סינון לפי טווח/קידומת"
סיבה: פילטר במעלה הזרם דוחה מספרים לפי טווח הספרה הראשונה (למשל מתייחס לספרה ראשונה מסוימת כ"לא תעודה אישית"), או שספרת הביקורת נכשלת כי המספר נשמר ב-8 ספרות והאפס המוביל אבד.
פתרון: כל תעודת זהות אישית משתמשת באותה בדיקת Luhn בת 9 ספרות ללא תלות בספרה הראשונה, ואין מיפוי אמין של מעמד לפי טווח. הוסיפו אפסים מובילים (`zfill(9)`) לפני האימות, והסירו כל רשימת היתר לפי טווח ספרה ראשונה. שימו לב שמספר בן 9 ספרות שמתחיל ב-5 הוא לרוב ישות רשומה ולא תעודה אישית.

### שגיאה: "אורך לא תואם / אפס מוביל נחתך"
סיבה: גיליון אלקטרוני, parser של JSON או עמודה מספרית הפילו את האפס המוביל (למשל `012345678` שנשמר כ-integer הופך ל-`12345678`).
פתרון: שמרו תמיד את התעודה כמחרוזת. בקריאה הוסיפו אפסים משמאל לאורך 9 עם `zfill(9)` (Python) או `padStart(9, '0')` (JS) לפני שמריצים את הבדיקה. דחו רק אחרי הריפוד.

### שגיאה: "קלט לא תקין, יש מקפים או רווחים בתעודה"
סיבה: המשתמש הדביק מספר חברה או עמותה מעוצב כמו `51-530820-3` או `58 012345 3`.
פתרון: מסירים רק את תווי ההפרדה (רווח, סוגי המקפים, רווח בלתי-שביר ורווח צר, תווים חסרי רוחב), ומקצצים רווחים, טאבים, ירידות שורה וסימני LRM/RLM רק בקצוות (טאב או ירידת שורה בתוך המספר הם קלט פגום), לפני בדיקת האורך, ואז `zfill(9)`. גם הצורה המעוצבת וגם הספרות הגולמיות חייבות לעבור את אותה בדיקה.

**לא מסירים כל תו שאינו ספרה.** `re.sub(r'[^0-9]', '', id)` נראה כמו אותו דבר והוא לא: הוא מוחק את התווים החריגים במקום לדווח עליהם, כך ש-`62819482.1` הופך לתעודה **תקינה** `628194821`, ו-`""`, `"abc"` ו-`"!!!!!!!!!"` כולם הופכים ל-`000000000`. משתמשים בקבוצת מפרידים מפורשת, וכל דבר אחר נדחה כקלט פגום. גם לא משתמשים ב-`\d` או ב-`str.isdigit()` לבדיקת הספרות: ב-Python שניהם מתאימים גם לספרות ערביות-הודיות, ולכן `re.sub(r'\D', '', id)` מעביר אותן הלאה ל-`int()`.

### שגיאה: "אי אפשר להבחין בין שדה ריק לתעודה שגויה"
סיבה: המאמת מחזיר בוליאני אחד, ולכן "המשתמש השאיר ריק", "המשתמש הקליד אותיות" ו"התעודה נכשלת בספרת הביקורת" מגיעים כולם כ-`False`, והטופס מציג את ההודעה הלא נכונה.
פתרון: מחזירים את הסיבה ולא רק את הפסק. `scripts/validate_id.py` מבחין בין השלושה בקודי יציאה: **0** תקין, **1** תעודה תקינה מבנית שנכשלת בספרת הביקורת, **2** קלט פגום, עם הסיבה ב-stdout. מסתמכים על קוד היציאה ולא על הטקסט.

### שגיאה: "קלט בן 9 ספרות אבל האלגוריתם נכשל"
סיבה: לרוב מדובר בהחלפת מקום בין שתי ספרות או שגיאת הקלדה בגוף המספר, לא בספרת הביקורת. סיבה נוספת: מדובר במספר אישי צבאי, שהוא מזהה נפרד של צה"ל שהסקיל לא מתעד עבורו ספרת ביקורת (ראו מלכודות נפוצות), ולכן כישלון לא אומר עליו דבר.
פתרון: בקשו מהמשתמש להקליד מחדש מהמסמך המקורי. אם זה עדיין נכשל והמשתמש מתעקש שהמספר נכון, הציעו אימות חיצוני מול הרשם המנפיק; לא "מתקנים" ספרת ביקורת בלי לדעת מה האמת.
